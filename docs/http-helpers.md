# Готовые функции в core/http.py

В прекоде есть небольшой набор общих функций для Django views. Они избавляют от повторения проверки метода, разбора JSON и формирования ошибок. Регистрация и вход в `core/auth.py` уже используют их — этот файл можно читать как пример.

Функции не реализуют правила SprintBoard. Участие в проекте, права владельца, архив и переходы статусов вы проверяете в `board/`. Распределение этой логики между views и отдельными модулями выбираете сами.

## Метод, сессия и ошибка

`@endpoint("GET", "POST")` разрешает указанные методы. Другой метод получает 405 `method_not_allowed`. Если пользователь не вошёл, ответ — 401 `authentication_required`. Параметр `public=True` отключает только требование входа; его используют публичные операции авторизации и health.

Внутри view можно вызвать `raise APIError("forbidden", 403)`. Декоратор перехватит именно `APIError` и вернёт `{"error": "forbidden"}` с кодом 403. У `APIError` код HTTP по умолчанию — 400. Другие исключения декоратор не превращает в ошибки API.

В `board/views.py` декораторы уже стоят над заглушками. Они **не проверяют**, принадлежит ли проект пользователю. Эта проверка нужна до чтения чужих данных или изменения записей.

CSRF проверяет middleware Django до вызова view. Функция `csrf_failure(request, reason="")` только формирует JSON-ответ 403 `csrf_failed` при отказе; она подключена в `config/settings.py`. Декоратор `endpoint` CSRF не отключает.

## Тело запроса

`body(request, allowed, required=())` возвращает словарь из JSON-тела:

- неподходящий Content-Type — 415 `unsupported_media_type`;
- неверный JSON или JSON не в виде объекта — 400 `invalid_json`;
- неизвестные поля или отсутствие обязательных — 400 `invalid_fields`.

Например, в обработчике создания проекта можно разобрать поля так:

```python
data = body(request, {"name", "description"}, {"name"})
name = text(data["name"], 100)
description = text(data.get("description", ""), 2000, blank=True)
```

Этот фрагмент ещё не создаёт проект. `body` проверяет набор ключей, а `text` — значения. Пустой PATCH надо отклонить отдельно: вызов `body` без обязательных полей допускает `{}`.

## Значения полей

`text(value, maximum, blank=False)` проверяет тип строки, обрезает пробелы по краям и проверяет длину. Пустая строка допускается только при `blank=True`. Возвращает очищенную строку; при ошибке вызывает `APIError("invalid_value")`.

`positive_id(value)` принимает положительное целое число и возвращает его. Строка `"2"`, `true`, ноль и отрицательные числа дают 400 `invalid_value`. Функция не ищет пользователя в базе и не проверяет, состоит ли он в проекте. Для `assignee_id=null` пропустите эту проверку: `null` здесь означает отсутствие исполнителя.

Допустимые статусы и приоритеты, календарные даты, принадлежность исполнителя проекту проверяются вашим кодом по требованиям.

## Параметры и страницы

`query(request, allowed=())` проверяет имена query-параметров и запрещает повторение одного имени. `page` и `page_size` разрешены всегда; дополнительные имена передаются в `allowed`. Нарушение — 400 `invalid_query`. Значения фильтров эта функция не проверяет.

`page(request, queryset, serialize)` проверяет числовые `page` и `page_size`, считает записи, выделяет страницу и возвращает JSON `{"count": ..., "results": [...]}`. Функция `serialize` преобразует одну запись в словарь; её нужно написать самостоятельно. До вызова `page` ограничьте QuerySet доступными данными, примените фильтры и сортировку.

Эти функции дополняют друг друга: `query` не формирует страницу, а `page` не запрещает неизвестные или повторяющиеся query-параметры. Для сводки параметры запрещены вообще; одного `query(request)` недостаточно, потому что он допускает `page` и `page_size`.

## Ответ без тела

`no_content()` возвращает HTTP 204 без тела. Подходит для успешного удаления и выхода. При других успешных ответах используйте обычный `JsonResponse`.

`health(request)` уже отвечает на `GET /api/health/` и помогает проверить запуск сервера. Переписывать его не нужно.

## Как проверить, что функции подходят задаче

В `Ask` передайте `@/core/http.py`, нужный обработчик и раздел требований. Попросите отделить проверки, которые уже выполняются, от тех, которые предстоит добавить. Например, для создания задачи отдельно нужны проверка участия, состояния архива и исполнителя. Не просите агента заново писать готовую регистрацию ради этого сценария.
