# SprintBoard: требования и контракт API

Этот файл задаёт поведение, с которым сверяются автотесты. Вы сами выбираете модели и распределяете код между view и сервисами. URL, поля, правила доступа и коды ответов должны совпасть с описанием. OpenAPI-документ вы составляете самостоятельно в `openapi.yaml`.

## Как пользоваться этим документом

Это точные требования к бэкенду SprintBoard и его OpenAPI. Сначала прочитайте сценарий сервиса, затем обращайтесь к соответствующим разделам при разработке:

- разделы 2–3 — общие правила API и готовая авторизация;
- раздел 4 — проекты, участники и их права;
- разделы 5–7 — задачи, переходы статусов, списки, комментарии и история;
- разделы 8–9 — сводка, архив и порядок проверок доступа;
- разделы 10–11 — OpenAPI и состав работы для сдачи.

Браузерный интерфейс не входит в обязательную часть. Все действия в сценарии ниже выполняются через HTTP API. Команды запуска находятся в README, а план работы с агентом — в уроке «Описание проектной работы». Для проверки через HTTP используйте готовую коллекцию из `postman/`; её запуск описан в `postman/README.md`. Готовые функции прекода объяснены в `docs/http-helpers.md`.

## 1. Сценарий работы сервиса

Марина и Антон регистрируются и входят в свои аккаунты. Марина создаёт проект «Сайт конференции» и становится его владельцем. Она может менять настройки проекта и добавлять зарегистрированных пользователей по логину. Добавив Антона, она предоставляет ему доступ к проекту.

Антон как участник может создавать и редактировать задачи, назначать исполнителя из числа участников, менять статус по разрешённым переходам и добавлять комментарии. Управлять настройками проекта и составом участников он не может. Марина может работать с задачами наравне с участниками. Удалить задачу может владелец проекта или её создатель, пока он состоит в проекте; назначение исполнителем само по себе права удаления не даёт.

Антон заводит задачу «Добавить программу выступлений», назначает себя исполнителем и указывает срок. Начальный статус — `todo`. По ходу работы он переводит задачу в `in_progress`, оставляет комментарий и переводит её в `review`. Марина проверяет результат и переводит задачу в `done`. Это пример распределения работы: все перечисленные переходы доступны любому участнику, а переход напрямую из `todo` в `done` запрещён.

Участники находят задачи по тексту и фильтрам, читают комментарии и историю изменений. Сводка показывает количество задач в каждом статусе и число просроченных. После завершения проекта Марина архивирует его: участники могут читать данные, но больше не могут менять задачи и состав участников. Возобновить работу может Марина, сняв архивирование.

Олег тоже зарегистрирован в сервисе, но не состоит в этом проекте. Он не видит его в списке и не получает доступ по известному ID. Публичного просмотра и роли наблюдателя нет. Если участника удалить, он тоже потеряет доступ, даже к созданным им задачам.

## 2. Общие правила

- Python 3.11+, Django 5.2, SQLite; обычные Django views и `JsonResponse`. DRF, Redis, Celery, Docker и внешние API для обязательной части не нужны.
- URL заканчиваются `/`. Все тела POST/PATCH — JSON-объекты с `Content-Type: application/json`. Для DELETE тело не нужно.
- Все успешные ответы, кроме 204, — JSON. Ответ 204 не содержит тела.
- Ошибка имеет вид `{"error": "код"}`. Дополнительные поля в ответы не добавляйте. Разрешены только перечисленные поля запросов; неизвестное или пропущенное обязательное поле — 400 `invalid_fields`. Пустой PATCH тоже возвращает эту ошибку.
- Синтаксически неверный JSON, массив или `null` вместо объекта — 400 `invalid_json`. Неподходящий Content-Type — 415 `unsupported_media_type`.
- Неверный тип, длина или значение поля — 400 `invalid_value`, кроме специально названных ниже ошибок. JSON `true` не является допустимым ID.
- Текстовые поля проекта, задачи и комментария обрезаются по краям (`strip`). Обязательные строки не могут состоять из пробелов. Длины проверяются после обрезки. Описание может быть пустым, но не `null`.
- ID — положительное целое число; ID и даты создания назначает сервер. Время — строка ISO 8601 с часовым поясом. Часовой пояс проекта — UTC.
- Неподдерживаемый метод на существующем маршруте — 405 `method_not_allowed`. Произвольные неизвестные URL не входят в JSON-контракт задания.
- В готовом приложении не должно быть заглушек 501. В прекоде они намеренно обозначают ещё не реализованные операции.

## 3. Готовая регистрация и вход

Эти операции уже реализованы в `core/`. Переписывать механизм входа не требуется. В проекте используется стандартный `User`: логин `username`, а не email.

- `GET /api/health/` → 200 `{"status": "ok"}`.
- `GET /api/auth/csrf/` → 200 `{"csrfToken": "..."}` и cookie `csrftoken`.
- `POST /api/auth/register/` с `username` и `password` → 201 `{"id": 1, "username": "marina"}`. Регистрация не выполняет вход.
- `POST /api/auth/login/` с теми же полями → 200 с ID и логином, а также cookie сессии `sessionid`. Неверные учётные данные → 401 `invalid_credentials`.
- `GET /api/auth/me/` → 200 с ID и логином текущего пользователя.
- `POST /api/auth/logout/` → 204, сессия завершается.

Логин: от 3 до 30 латинских букв, цифр или символов `_`, `.`, `-`; регистр учитывается. Пароль: от 8 до 128 символов. Короткий пароль → 400 `invalid_password`, занятый логин → 409 `username_taken`. Пароли хранятся средствами Django, в ответах их нет.

Каждый POST, PATCH и DELETE, включая регистрацию и вход, требует CSRF-токен в заголовке `X-CSRFToken` и соответствующую cookie. После входа получите свежий токен. Отсутствующий или неверный токен → 403 `csrf_failed` до выполнения view. Не отключайте CSRF для прохождения тестов.

Операции проектов и задач доступны только после входа. Без сессии они возвращают 401 `authentication_required`; для изменяющего запроса подразумевается, что CSRF-проверка уже пройдена. Не возвращайте перенаправление на страницу входа.

## 4. Проекты и участники

### Проект

Поля ответа: `id`, `name` (1–100 символов), `description` (до 2000), `owner_id`, `archived` (boolean), `created_at`.

`POST /api/projects/` принимает обязательное `name` и необязательное `description` (по умолчанию `""`). Возвращает проект со статусом 201. Создатель становится владельцем и участником, `archived` изначально `false`.

`GET /api/projects/` возвращает список проектов текущего пользователя, включая архивные. Сортировка: сначала новые по `created_at`, при равенстве — по убыванию ID.

`GET /api/projects/{project_id}/` возвращает проект со статусом 200.

`PATCH /api/projects/{project_id}/` разрешён только владельцу. Разрешённые поля: `name`, `description`, `archived`. Возвращает изменённый проект со статусом 200. Владелец может редактировать эти поля и у архивного проекта, в том числе снять архивирование. Передача владения и удаление проекта не входят в задание.

### Участники

Роль определяется внутри проекта. Один пользователь может быть владельцем одного проекта и обычным участником другого. `is_staff` не предоставляет права в чужих проектах.

`GET /api/projects/{project_id}/members/` возвращает участников в порядке возрастания ID пользователя. Поля одного участника: `id` (именно ID пользователя), `username`, `role` (`owner` или `member`).

`POST /api/projects/{project_id}/members/` принимает `{"username": "anton"}`. Только владелец может добавить уже зарегистрированного пользователя. Успех → 201 с данными участника; повторное добавление → 409 `membership_exists`; неизвестный логин → 404 `user_not_found`. Приглашений по почте нет.

`DELETE /api/projects/{project_id}/members/{user_id}/` удаляет участника и возвращает 204. Доступно только владельцу. Удалить владельца нельзя: 409 `owner_required`. Если пользователь назначен исполнителем хотя бы одной задачи проекта, включая завершённую, верните 409 `member_in_use`. Сначала нужно снять назначения или выбрать другого исполнителя. Если участника нет — 404 `not_found`.

После удаления участник теряет доступ к проекту, его задачам, комментариям, истории и сводке. Его старые задачи и комментарии сохраняют автора. Авторство само по себе не возвращает доступ.

## 5. Задачи

### Поля

Поля ответа задачи:

```json
{
  "id": 1,
  "project_id": 1,
  "title": "Добавить программу выступлений",
  "description": "Вывести список докладов по дням",
  "reporter_id": 2,
  "assignee_id": 2,
  "priority": "medium",
  "status": "todo",
  "due_date": "2030-05-20",
  "created_at": "2030-05-10T09:00:00+00:00",
  "updated_at": "2030-05-10T09:00:00+00:00"
}
```

`title`: 1–200 символов. `description`: до 10 000, по умолчанию `""`. `priority`: `low`, `medium` или `high`, по умолчанию `medium`. `due_date`: существующая календарная дата строго в формате `YYYY-MM-DD` или `null`, по умолчанию `null`. Срок в прошлом допустим.

`reporter_id` — создатель задачи, определяется из сессии. `assignee_id` — участник того же проекта или `null`, по умолчанию `null`. Назначение пользователя вне проекта или несуществующего пользователя → 400 `invalid_assignee`. Тип ID проверяется отдельно: например, строка вместо числа → 400 `invalid_value`.

### Операции

`POST /api/projects/{project_id}/tasks/` принимает обязательное `title` и необязательные `description`, `priority`, `assignee_id`, `due_date`. Любой участник может создать задачу. Успех → 201 с задачей, статус всегда `todo`.

`GET /api/tasks/{task_id}/` → 200 с задачей.

`PATCH /api/tasks/{task_id}/` позволяет любому участнику менять `title`, `description`, `priority`, `assignee_id`, `due_date`. Успех → 200 с задачей. `null` снимает исполнителя или срок. Нельзя подменять проект, автора, ID, даты создания или статус через этот endpoint.

Если PATCH не изменяет значения, верните текущую задачу без новой записи истории и без изменения `updated_at`. Ошибка в одном поле отменяет весь запрос: остальные поля тоже должны остаться прежними.

`DELETE /api/tasks/{task_id}/` доступен владельцу проекта или создателю задачи. Остальные участники получают 403 `forbidden`. Исполнитель не получает право удаления только за счёт назначения. Успех → 204; комментарии и история удалённой задачи больше недоступны.

### Переходы статусов

`POST /api/tasks/{task_id}/transition/` принимает `{"status": "in_progress"}` и возвращает задачу со статусом 200. Доступно любому участнику проекта.

Допустимые переходы:

- `todo` → `in_progress`;
- `in_progress` → `todo` или `review`;
- `review` → `in_progress` или `done`;
- `done` → `todo` (повторное открытие).

Остальные переходы, включая переход в текущий статус, → 409 `invalid_transition`. Неизвестное имя статуса или неверный тип → 400 `invalid_value`. При отказе задача, `updated_at` и история не меняются.

## 6. Поиск, фильтры и страницы

`GET /api/projects/{project_id}/tasks/` возвращает задачи только этого проекта. Сортировка: `created_at` по убыванию, затем ID по убыванию.

Необязательные параметры:

- `status`: один из четырёх статусов;
- `priority`: один из трёх приоритетов;
- `assignee_id`: положительное целое число; если таких назначений нет, список пуст;
- `q`: непустая после обрезки строка до 200 символов; поиск подстроки в заголовке или описании. Для обязательной части используется поведение поиска SQLite/Django; полноценный поиск с морфологией и нормализацией Unicode не требуется;
- `overdue`: строго `true` или `false`.

Задача просрочена, если её `due_date` раньше сегодняшней даты в UTC и статус не `done`. Срок сегодня и отсутствие срока не считаются просрочкой. `overdue=false` выбирает все непросроченные задачи. Все переданные фильтры работают одновременно через логическое И.

Списки проектов, участников, задач, комментариев и истории поддерживают `page` (по умолчанию 1) и `page_size` (по умолчанию 20, максимум 100). Формат ответа одинаков:

```json
{"count": 42, "results": []}
```

`count` — число записей после фильтров, но до выделения страницы. За пределами последней страницы возвращается пустой `results` и тот же `count`.

Неверный параметр, пустое числовое значение, ноль, отрицательное число, дробь, повтор одного параметра или неизвестное имя параметра → 400 `invalid_query`. Числовые query-параметры записываются ASCII-цифрами, максимум девять цифр. Все списки, кроме списка задач, принимают только параметры страниц. На сводке query-параметры не предусмотрены. Для детальных GET-запросов обработка query-параметров не оценивается.

## 7. Комментарии и история

`GET /api/tasks/{task_id}/comments/` возвращает комментарии от старых к новым (`created_at`, затем ID по возрастанию).

`POST /api/tasks/{task_id}/comments/` принимает `{"text": "Готово к проверке"}`. Текст: 1–2000 символов. Любой участник может добавить комментарий. Успех → 201; поля ответа: `id`, `task_id`, `author_id`, `text`, `created_at`. Автор определяется из сессии. Редактирование и удаление комментариев не нужны.

`GET /api/tasks/{task_id}/history/` возвращает события от старых к новым. Поля события: `id`, `task_id`, `actor_id`, `kind`, `data`, `created_at`. История доступна только для чтения, отдельного API создания событий нет.

Обязательные события:

- Создание задачи: `kind=task_created`, `data={}`.
- Успешный PATCH с изменениями: одно событие `kind=task_updated`; `data={"changes": {"имя_поля": {"old": "старое значение", "new": "новое значение"}}}`. Только реально изменённые поля; ID остаются числами, отсутствие значения — `null`, даты — строки.
- Переход статуса: `kind=status_changed`, `data={"from": "todo", "to": "in_progress"}`.
- Добавление комментария: `kind=comment_added`, `data={"comment_id": 1}`.

В `actor_id` записывается пользователь, выполнивший действие. Изменение данных и запись события выполняются в одной транзакции. Не должно быть ситуации, когда действие сохранено, а история — нет. Отклонённые запросы и PATCH без изменений новых событий не создают.

## 8. Сводка и архивирование

`GET /api/projects/{project_id}/summary/` возвращает 200:

```json
{"total": 4, "by_status": {"todo": 3, "in_progress": 0, "review": 0, "done": 1}, "overdue": 1}
```

В сводке только задачи выбранного проекта. Все четыре статуса присутствуют даже при нулевых значениях. Правило просрочки совпадает с фильтром списка. У пустого проекта все значения нулевые.

Архивирование блокирует создание, редактирование и удаление задач, переходы статусов, добавление комментариев, добавление и удаление участников: 409 `project_archived`. Чтение остаётся доступным участникам. Владелец может изменить сам проект и вернуть `archived=false`.

## 9. Порядок проверки доступа

Сначала Django проверяет CSRF у изменяющего запроса. Затем view проверяет метод и сессию. Для ресурса выясняем участие в проекте, после этого — право на операцию, состояние архива и входные данные.

Авторизованный посторонний получает одинаковый 404 `not_found` для отсутствующего и недоступного проекта/задачи. Обычный участник получает 403 `forbidden`, если пытается управлять проектом, составом участников или удалить чужую задачу. Это правило действует и в архивном проекте; 409 об архиве получают только пользователи, которым сама операция разрешена.

В каждом случае отказа проверьте не только ответ, но и данные после запроса. Чужой пользователь не должен изменить задачу, добавить комментарий или оставить событие в истории.

## 10. OpenAPI и собственные проверки

Опишите все 16 маршрутов и 23 операции в `openapi.yaml`, включая готовую авторизацию. Версия формата — OpenAPI 3.0.3, ссылки `$ref` только внутри файла. Для каждой операции нужны уникальный `operationId`, параметры, тело запроса (если есть), ответы и ошибки. Для списков укажите пагинацию, для задач — все фильтры.

Опишите cookie `sessionid` как схему аутентификации и обязательный заголовок `X-CSRFToken` для POST/PATCH/DELETE. У четырёх публичных маршрутов (`health`, `csrf`, `register`, `login`) сессия не требуется; CSRF для двух POST всё равно обязателен.

Схемы ответов должны содержать поля с типами, обязательностью, допустимыми значениями и `nullable`, где разрешён `null`. Пустая схема `{}` не считается описанием ответа. В 204 не указывайте тело. Названия компонентов можно выбирать самостоятельно; в задаче нет рекурсивных схем, циклические `$ref` не используйте.

Рекомендуем добавлять собственные тесты в `student_tests/`: например, проверить неизменность данных после отказа. Выберите сценарии, которые уточняют готовые проверки, а не повторяют их дословно. Собственные тесты и записи в `docs/ai-worklog.md` нужны для практики; их количество и качество не оцениваются при автоматической приёмке.

## 11. Что сдавать

Подготовьте код проекта, зависимости, миграции и `openapi.yaml` в репозитории, выданном для задания на платформе. Отправьте изменения в этот репозиторий, затем выполните инструкцию в форме сдачи. Не создавайте Fork или отдельный репозиторий вместо связанного со сдачей. Работа принята, когда все автотесты на платформе пройдены. При ошибке изучите результат проверки, исправьте причину и отправьте работу повторно.

Ручного ревью не будет. Автотесты не оценивают качество запросов к AI, понимание кода, README и журнал решений. Рекомендуем сохранять план, полезные итерации и результаты проверок для себя. Журнал и собственные тесты не являются условием сдачи. Полную переписку, секреты и реальные пользовательские данные публиковать не нужно.

Фронтенд не требуется: для проверки пользовательского сценария предоставлена Postman-коллекция. Её результаты помогают подготовиться, но не заменяют автотесты на платформе. Экспорт отчёта Postman для сдачи не нужен. Деплой, уведомления, вложения, спринты, произвольные workflow, JWT, WebSocket и интеграции с Jira не требуются.
