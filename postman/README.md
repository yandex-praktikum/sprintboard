# Проверка SprintBoard в Postman

Файл `SprintBoard.postman_collection.json` содержит готовый сценарий работы сервиса. Писать фронтенд или вручную собирать все запросы не нужно. Коллекция проверяет настоящий HTTP API: cookie сессии, CSRF, JSON-ответы и изменения данных.

## Запуск

1. Установите зависимости, примените миграции и запустите `python manage.py runserver` по README проекта. Оставьте сервер работающим.
2. Импортируйте `postman/SprintBoard.postman_collection.json` в настольное приложение Postman. Можно перетащить JSON-файл в окно импорта. Порядок импорта описан в [документации Postman](https://learning.postman.com/docs/getting-started/importing-and-exporting/importing-data).
3. У коллекции есть одна настройка `base_url`, по умолчанию `http://127.0.0.1:8000`. Если сервер работает на другом локальном порту, поменяйте её. Отдельное окружение импортировать не нужно. Не смешивайте `localhost` и `127.0.0.1`: cookie относятся к адресу сервера.
4. Выберите коллекцию целиком и откройте **Run**. Запускайте локально, с одной итерацией, сохранив порядок запросов. Cookies должны быть включены. Для первого запуска не передавайте сохранённые cookies; коллекция получит необходимые сама. Интерфейс запуска описан в [Collection Runner](https://learning.postman.com/docs/tests-and-scripts/running-collections/intro-to-collection-runs).
5. Посмотрите результаты проверок и откройте запрос, на котором появилась первая ошибка. В названии указано ожидаемое действие, а в Scripts / Post-response — проверки ответа.

Коллекция использует локальные переменные текущего запуска для пароля, токенов и ID. Они не становятся настройками коллекции. Поэтому для повторного сценария снова запускайте коллекцию с начала; отдельное нажатие Send посередине не восстановит данные прошлого запуска.

Каждый запуск создаёт трёх новых учебных пользователей и проект в вашей локальной базе. Учебная задача удаляется в конце успешного сценария, пользователи и проект остаются. Повторный запуск не требует очищать базу. Используйте коллекцию только на локальном учебном сервере.

## Что происходит в сценарии

- **01 — Подготовка пользователей.** Проверка health, получение CSRF, завершение прежней сессии и регистрация Марины, Антона и Олега. Эту папку можно запускать отдельно уже на прекоде.
- **02 — Марина создаёт проект.** Вход владельца, создание и изменение проекта, добавление Антона, просмотр участников.
- **03 — Антон работает с задачей.** Создание, редактирование, комментарий, переходы, история, фильтры и сводка. Проверяем также отказ при неверной дате и недопустимом переходе.
- **04 — Олег не получает доступ.** Проверяем, что посторонний не видит проект и не меняет задачу по известному ID.
- **05 — Марина завершает и архивирует проект.** Проверяем, что отказы не изменили данные, завершаем задачу, включаем и снимаем архив, удаляем Антона после снятия назначения.
- **06 — Бывший участник теряет доступ.** Антон не может читать или удалять свою прежнюю задачу. Владелец удаляет её, проверяет сводку и выходит из аккаунта.

Перед каждым входом коллекция получает CSRF-токен, а после входа обновляет его. Между пользователями выполняется выход. Не отключайте CSRF в приложении, если запрос не прошёл: сначала проверьте предыдущие запросы авторизации.

## Как читать результат

403, 404 и 409 в этой коллекции не всегда означают провал. Например, запрос Олега к чужой задаче должен вернуть 404 — это успешная проверка запрета доступа. Ориентируйтесь на результаты assertions и ожидаемый код в скрипте запроса.

При неожиданном HTTP-статусе сценарий останавливается: продолжать с несозданным проектом или без сессии бессмысленно. Исправьте первую причину и запустите коллекцию заново. Если статус ожидаемый, но тело неверное, ошибка будет видна в проверках ответа.

На исходном прекоде весь сценарий не пройдёт: проекты и задачи ещё возвращают 501. Для начального этапа достаточно папки 01 и шести Django-тестов авторизации. Остальные папки зависят от предыдущих, поэтому полный запуск имеет смысл после реализации бэкенда.

Postman помогает посмотреть на сервис снаружи и разобрать ответы. Он не проверяет полноту OpenAPI и не заменяет 43 теста из `acceptance/` или автоматическую проверку на платформе. Экспорт результатов Postman для сдачи не требуется.
