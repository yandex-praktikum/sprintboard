# SprintBoard — прекод

Вы разрабатываете бэкенд командного трекера задач на Django и спецификацию OpenAPI. Пользователи создают проекты, распределяют задачи и обсуждают работу. Обязательная часть — JSON API; браузерный интерфейс для сдачи не требуется.

Точные поля, маршруты и правила: [требования к API](docs/requirements.md). Порядок разработки и применение навыков спринта описаны в уроке «Описание проектной работы».

## С какого репозитория начать

Используйте репозиторий, который вы получили для этого задания на платформе. Он уже содержит прекод и связан со сдачей. **Не создавайте Fork или другой репозиторий вместо него.**

Скопируйте адрес своего учебного репозитория и подставьте его вместо `URL_РЕПОЗИТОРИЯ_С_ПЛАТФОРМЫ`:

```bash
git clone URL_РЕПОЗИТОРИЯ_С_ПЛАТФОРМЫ
```

Перейдите в созданный каталог командой `cd`. Название каталога зависит от имени выданного репозитория. Если у вас уже есть его локальная копия, продолжайте работу в ней.

## Что уже работает и что предстоит сделать

Регистрация, вход, выход, проверка сессии и CSRF уже готовы в `core/`. Шесть тестов `acceptance.test_bootstrap` должны проходить сразу после установки.

В `board/` заданы URL и обработчики, но операции пока возвращают 501 `not_implemented`. Модели предметной области нужно написать. В `openapi.yaml` описана только проверка доступности сервера. Поэтому полный набор тестов в прекоде **не проходит** — это ожидаемое начальное состояние.

Вам предстоит реализовать проекты и участников, задачи и переходы статусов, комментарии и историю, поиск, страницы, сводку и архивирование. OpenAPI нужно дополнить до полного описания API. Условия каждого сценария приведены в `docs/requirements.md`.

## Запуск

Нужен Python 3.11 или новее. Команды ниже выполняются из каталога репозитория, где находится `manage.py`.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

В Windows вместо `source` выполните `.venv\Scripts\activate`. Если команда `python` не найдена, используйте `python3` (Windows: `py -3`).

Откройте http://127.0.0.1:8000/api/health/ — сервер должен ответить `{"status": "ok"}`. Стартовой HTML-страницы и админки здесь нет. Остановить сервер можно сочетанием Ctrl+C.

Проект рассчитан на локальную учебную разработку: SQLite, DEBUG и учебный SECRET_KEY. Не используйте эти настройки для публичного сервера. Значения `DJANGO_SECRET_KEY` и `DJANGO_DEBUG` можно задать переменными окружения.

## Проверка

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
```

Команда `test` должна найти тесты. Сообщение «Ran 0 tests» не означает, что задание выполнено: проверьте, что терминал открыт в каталоге с `manage.py`. Тестовая база создаётся отдельно от вашей рабочей базы.

Проверки по частям:

```bash
python manage.py test acceptance.test_bootstrap
python manage.py test acceptance.test_projects
python manage.py test acceptance.test_tasks acceptance.test_workflow
python manage.py test acceptance.test_openapi
python manage.py test student_tests
```

`acceptance/` — готовые проверки поведения API, а не образец архитектуры. Они не импортируют ваши модели. Не удаляйте и не ослабляйте эти проверки. Собственные сценарии добавляйте в `student_tests/`.

Обычный Django test client пропускает CSRF-проверку; в наборе есть отдельные тесты с `enforce_csrf_checks=True`. Не переносите упрощения тестового клиента в приложение. Пример реальных запросов с cookie и CSRF есть в `acceptance/test_bootstrap.py`.

## Где что лежит

- `docs/requirements.md` — поведение API, поля, права и ошибки.
- `openapi.yaml` — описание API в OpenAPI 3.0.3.
- `core/auth.py` — готовые регистрация, вход, выход и проверка сессии.
- `core/http.py` — проверки метода и входа, разбор JSON, ошибки и пагинация. Границы этих функций объяснены в [docs/http-helpers.md](docs/http-helpers.md); права на проекты и задачи они не реализуют.
- `board/` — проекты, участники, задачи, комментарии и история.
- `acceptance/` — 43 готовых тестовых метода, включая проверку OpenAPI.
- `student_tests/` — ваши дополнительные проверки.
- `postman/` — готовая коллекция и [инструкция](postman/README.md) для проверки сервиса без фронтенда.
- `docs/tasks/` — карточки контекста отдельных задач; внутри есть каркас.
- `docs/ai-worklog.md` — необязательный общий журнал решений и проверок при работе с AI.
- `docs/ci-workflow.yml` — необязательный шаблон GitHub Actions. Чтобы включить CI, скопируйте его в `.github/workflows/tests.yml` через аккаунт с правом редактировать workflows. По умолчанию CI не включён.

Для проверки через HTTP используйте готовую [Postman-коллекцию](postman/SprintBoard.postman_collection.json). Запустите Django-сервер и импортируйте JSON-файл в Postman, затем выполните коллекцию целиком через Collection Runner. Она сама подготовит пользователей, сессии и CSRF-токены. Полная инструкция и ожидаемые результаты — в [postman/README.md](postman/README.md). На исходном прекоде можно отдельно запустить папку 01; полный сценарий требует реализованного бэкенда. Коллекция не заменяет Django-тесты и сдачу на платформе.


## Порядок работы и сдача

Начните с требований и плана. Реализуйте по одному сценарию, например создание проекта или добавление участника: передайте агенту нужный раздел требований, проверьте предложенный план, затем код и результат тестов. Историю добавляйте вместе с операциями над задачами, а OpenAPI дополняйте по мере реализации.

После добавления моделей создайте и примените миграции:

```bash
python manage.py makemigrations board
python manage.py migrate
```

В конце должны проходить все 43 готовых тестовых метода. Миграции сохраните в репозитории вместе с кодом, зависимостями и `openapi.yaml`. Локальную базу, виртуальное окружение и секреты не коммитьте.

Отправьте изменения в тот же репозиторий, который связан с заданием на платформе, и выполните инструкцию в форме сдачи. Работа принята, когда все автотесты на платформе пройдены. При ошибке исправьте причину и отправьте новую версию. Локальный запуск тестов не заменяет отправку на платформу.

Ручного ревью не будет. Собственные тесты, карточки контекста, журнал AI и настройка GitHub Actions помогают в работе, но не являются дополнительными условиями приёмки. Фронтенд для выполнения задания не требуется.
